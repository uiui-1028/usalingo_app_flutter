# Usalingo Anki型学習コア仕様（SwiftUI Ver.2）

最終決定日: 2026-08-27

## 1. この仕様の位置づけ

この文書は、現在のSwiftUIアプリ `apps/ios-swiftui/` とSupabaseを対象にした正本です。旧Web版のMVP方針は引き継ぎません。

完成の境界は次の状態です。

> 運営が用意した公式コンテンツを、利用者がライブラリで探し、デッキから学習し、正しい復習予定と学習記録がSupabaseへ保存される。重要な処理は自動テストで守られている。

この段階では動作の正しさを優先し、正式なUIUX、通知、オフライン、App Store対応は後のフェーズで扱います。

## 2. 採用するAnki型の役割

UsalingoはAnkiのNote、Card Type、Card、Deckの分離を採用します。

| Usalingoで見えるもの | Ankiでの役割 | 責任 |
|---|---|---|
| 単語と関連情報 | Note | 英単語、意味、例文、画像・音声の参照など、運営が管理する元情報 |
| 出題方向 | Card Type | Noteのどの情報を表と裏に出すかを決める設計図 |
| 学習カード | Card | 利用者が実際に回答し、復習予定を持つ単位 |
| デッキ | Deck | 学習するCardをまとめる箱 |
| 学習進捗 | Cardの記録 | 利用者ごと、Cardごとに正誤、間隔、次回復習日を持つ |

### 確定ルール

- 1つのNoteから複数のCardを作れる。
- 1つのCardは1つのDeckに所属する。
- 同じNoteから作られたCardは兄弟カードとして扱う。
- 学習進捗の一意条件は `user_id + card_id` とする。
- 最初に有効にするCard Typeは「英語から日本語」の1種類とする。
- 「日本語から英語」などの逆向きCard Typeを後から追加できる構造にする。
- Ankiのファイル形式、プラグイン、テンプレートDSLとの互換は目的にしない。

## 3. 現在の構造から変えること

現在は `words` が元情報と学習カードの両方を兼ね、`deck_words` と `user_learning_progress.word_id` が単語へ直接つながっています。

移行後は、既存の公式コンテンツを消さずに次の責任へ分けます。

```text
words / word_meanings / example_contents
  ↓ Noteとして利用
card_templates
  ↓ 出題方向を定義
cards
  ├─ noteとなるword
  ├─ card_template
  └─ deck
user_card_progress
  └─ user + cardごとの学習記録
```

移行は新しいテーブル、既存データの変換、Swift側の切り替え、旧構造の停止という順に行います。既存データを確認せずに削除しません。

## 4. 学習と復習

### 学習の流れ

1. 初回は管理側の標準デッキを自動設定し、2回目以降は利用者がデッキ一覧から選ぶ。
2. デッキを選ぶと、設定画面を挟まず学習を始める。
3. 復習期限を迎えたCardと新しいCardから、SRSが次のCardを自動で決める。
4. 利用者は「正解」「不正解」の2択で答える。
5. 回答ごとに `user_id + card_id` の学習記録を保存する。
6. 現在出題可能なCardが0枚になったら、簡潔なCompleteを表示する。

固定の1セッション枚数、新規カード／復習カードの日次上限、新規のみ／復習のみの学習モードは初期要件に含めません。途中終了はCompleteではなく中断として保存します。

### その日に出すCard（2026-10-07 決定）

Ankiと同じく、一度解いたCardはその日のうちは出しません。

- 今日の分は「期限が今日までの復習Card」と「新規Card」だけです。期限前のCardを先取りで出す入口はありません。
- 期限は日付で判定します。区切りは端末の深夜0時です。たとえば昨日22時に解いたCardは、今日の0時から出ます。
- カード・5択・ペアは同じ学習記録を共有します。どれか1つで解いたCardは、3つすべてでその日は出ません。5択の間違いの選択肢には、今日解いたCardも使います。
- カードと5択で不正解だったCardは、その回の最後にもう一度出します。正解するまで繰り返します。
- やり直しの答えは学習記録を進めません。Ankiの再学習と同じく、罰（誤答数の加算と易しさ係数の減少）は最初の不正解の1回だけです。次に出すのは翌日になります。
- ペアにはやり直しがありません。一度でも組を間違えた語は、揃えたときに不正解として記録します。
- 音声（ラジオ）は今日の分に絞らず、全Cardを流します。答えも記録しません。リストの赤シート確認は、これまでどおり答えるたびに記録します。
- 回答を取り消すと、そのCardは今日の分に戻ります。
- 今日の分が0枚なら「今日の学習は完了です」と表示します。

### 復習アルゴリズム

現在実装済みの2択SM-2ハイブリッドを最初の標準アルゴリズムとして採用します。これはAnki型の自動復習を正解・不正解の2段階へ簡略化したもので、Ankiの4段階評価を完全に複製するものではありません。

- 1回目の正解: 1日後
- 2回目の正解: 6日後
- 3回目以降: 前回間隔 × 易しさ係数
- 不正解: 連続正解を0、間隔を1日、学習レベルを1へ戻す
- 誤答3回以上: 苦手Cardとして扱う

複数アルゴリズムや高度な調整はこの完成境界に含めません。

## 5. 公式ライブラリ

ライブラリにはリスト表示とPinterest型カード表示を用意します。

### Pinterest型カード表示

- 複数列でカードを並べる。
- イラストは縦長の比率へ切り抜き、領域いっぱいに表示する。
- 表示する情報はイラストと英単語だけにする。
- 意味、品詞、学習数値、説明文はカード一覧へ表示しない。
- 画像がない場合の代替表示を用意する。
- カードを選ぶと単語詳細または学習開始へ進める。

レイアウトの細かな余白、列数、文字サイズは正式UIUXフェーズで人間が決定します。

## 6. 公式コンテンツとメディア

画像、例文、音声そのものの制作は、このアプリ開発プロジェクトに含めません。別ルートで制作されたコンテンツをSupabaseへ格納し、アプリは参照して表示・再生します。

```text
別ルートのコンテンツ制作
  ↓
Supabase Database + Storage
  ↓
SwiftUIアプリが読み取り
```

### 音声ルール

- 端末のTTSで音声を生成しない。
- 運営が用意した `audio_asset_path` の音声ファイルだけを再生する。
- 音声がないCardでは再生ボタンを無効にする。
- 公式公開コンテンツは公開Storage URLから配信する。
- 音声生成方法や生成コストは別プロジェクトで管理する。

## 7. Supabaseの目標構造

最低限、次の責任を分離します。具体的なSQLは移行課題で作成し、本番適用前に人間が確認します。

詳細なER図、既存表との対応、移行・切り戻し順序は [`anki-data-model.md`](./anki-data-model.md) を正本とします。
公式コンテンツの必須列、Storageパス、欠損時動作、権限境界は [`official-content-contract.md`](./official-content-contract.md) を正本とします。

- 公式Note情報: 既存の `words`、`word_meanings`、`example_contents`
- Card Type: `card_templates`
- 学習単位: `cards`
- デッキ: `decks`
- Card単位の進捗: `user_card_progress`
- 公式画像・音声: Supabase Storage

利用者は公式コンテンツを読み取れますが、運営用データを変更できないRLSにします。利用者の学習記録は本人の行だけを読み書きできるようにします。

## 8. 自動テストの最低線

- NoteからCardが正しく作られる。
- Card Typeによって出題方向が変わる。
- Deckから対象Cardだけを取得できる。
- 学習進捗が `user_id + card_id` で分離される。
- 復習期限のCardが新規Cardより先に出る。
- 正解、不正解、習熟、苦手判定が仕様どおりになる。
- 画像・音声の参照パスを読み取れる。
- 音声がないCardで再生操作が無効になる。
